## 一、每条最差路径要看四个数字

打开某条路径的 `-path_type full` 报告，重点看：

```text
Data Path Delay
Logic Delay
Route Delay
Logic Levels
```
![对应位置](D:/chiplab/mytool/md_img/1.jpg)
可以按下面的方法判断：

### 情况 A：Logic Delay 高，Levels 多

例如：

```text
Data Path Delay: 11 ns
Logic Delay: 8 ns
Route Delay: 3 ns
Logic Levels:    27
```

这里逻辑级数确实较深，且占比高，是明显的逻辑深度问题。

处理思路是：

- 把组合计算分配到前后两个流水级；
- 把大选择器拆开；
- 把复杂判断提前译码；
- 必要时在中间增加寄存器。

### 情况 B：Route Delay 高，Logic Delay 不高

例如：

```text
Logic Delay: 4.942 ns
Route Delay: 11.244 ns
```

这通常不是“代码计算太复杂”，而是：

- 扇出太大；
- 源和负载距离太远；
- 一个信号跨越多个模块；
- 一个控制信号驱动了很多 RAM/寄存器；
- 总线位被大量逻辑共同使用。

这时直接加流水寄存器未必是最佳方法。可以考虑：

- 在负载附近复制寄存器；
- 把全局控制信号变成局部控制；
- 减少一个 bus bit 的扇出；
- 将低频控制路径单独寄存；
- 让 Cache 本地保存它需要的控制字段。

### 情况 C：Fanout 高

例如：

```text
net (fo=35, routed)
```

要先查看它到底驱动了哪些输入：

```tcl
set q_pin [get_pins {完整的寄存器路径/Q}]
set q_net [get_nets -of_objects $q_pin]

get_pins -leaf -of_objects $q_net
```

不要只看 timing schematic。timing schematic 只画当前最差路径的一条支路，`fo=35` 表示这根网总共连接了 35 个负载。

如果这 35 个负载分布在：

```text
EXE1
MEM
Icache
BHT
```

多个区域，那么这就是全局信号，不应该继续让它作为一个未经处理的公共控制线传播。

## 三、先给每一级建立“延迟预算”

当前时钟周期约为：

```text
16.25 ns
```

不要把目标直接定成 12 ns。先给自己一个有余量的目标，例如：

```text
目标周期：14 ns
布局布线余量：0.5~1 ns
可接受数据路径：约13~13.5 ns
```

那么当前各级距离 14 ns 的差距大约是：

| 流水级 | 当前延迟 | 距离 14 ns |
|---|---:|---:|
| preIF1 | 13.670 | 基本接近 |
| preIF2 | 8.183 | 还有约 5.8 ns |
| IF | 5.140 | 还有约 8.9 ns |
| ID | 13.469 | 基本接近 |
| EXE1 | 16.186 | 超出约 2.2 ns |
| EXE2 | 11.046 | 还有约 3.0 ns |
| MEM | 12.247 | 还有约 1.8 ns |
| WB | 15.846 | 超出约 1.8 ns |

这张表只能告诉你“哪些级值得处理”，不能直接告诉你具体怎么切。

## 四、判断逻辑应该往哪一级移动

看一条路径的起点和终点：

```text
起点寄存器属于谁？
组合逻辑属于谁？
终点寄存器属于谁？
```

例如：

```text
EXE1 bus_reg
→ ALU/比较/选择逻辑
→ EXE2 bus_reg
```

这是一条正常的 EXE1 计算路径。可以考虑把计算分成两部分。

但如果是：

```text
EXE1 bus_reg
→ cacop 判断
→ Icache cacop_this_cache_r
```

那不是普通 EXE1 数据通路，而是控制路径。应该考虑：

```text
EXE1 产生 cacop 请求
→ Core 或 Cache 接口寄存
→ Icache/Dcache 使用
```

而不是把 ALU 整级拆成两段。

## 五、切寄存器时必须成组切

不能只给某一个信号加寄存器。

如果一个信号从 EXE1 延迟到 EXE2，至少要同时考虑：

```text
数据：
alu_result
data_sram_addr
data_sram_wdata

控制：
mem_we
res_from_mem
cache_code
inst_cacop

异常：
ex_tlb_*
ex_ALE
EXE1_ex

流水控制：
valid
ready_go
allow_in
stall
cancel
```

否则会出现：

```text
地址已经是下一条指令的
控制信号还是上一条指令的
异常信息又来自更早的一条指令
```

这类错误比 timing violation 更危险。

## 六、每次只做一个“可验证切割”

一个完整的调整循环应该是：

```text
1. 选一条具体最差路径
2. 找到它的真实逻辑归属
3. 判断是逻辑深、布线长还是扇出大
4. 只做一个局部修改
5. 重新综合和布局布线
6. 比较 WNS、路径延迟、系统计数器
7. 功能仿真/跑测试
```

不要一次同时：

```text
加寄存器
改 ready_go
改 valid
改 cache 接口
改分支取消
```

否则即使 timing 变好，也无法知道是哪项修改造成的。

## 七、你现在可以按这个顺序练习

先不要改代码，拿 `05_EXE1_top60.rpt` 的第一条路径做手工分析：

```text
Source
Destination
Data Path Delay
Logic Delay
Route Delay
Logic Levels
Fanout
```

然后回答这五个问题：

1. 起点寄存器属于 EXE1 的哪一类字段？
2. 终点为什么在 Icache，而不是 EXE2/MEM？
3. 中间组合逻辑是在做数据计算还是控制判断？
4. Route Delay 是否明显大于 Logic Delay？
5. 这条信号是否可以在 Cache 接口附近单独寄存？

你能回答这五个问题后，基本就能自己判断应该：

```text
移动逻辑
复制信号
降低扇出
局部加寄存器
还是完全不需要加流水级
```

当前这些报告已经告诉我们一件事：**不是所有级都需要拆，真正应该优先分析的是 EXE1 和 WB 的跨模块控制路径；preIF2、IF 目前有明显余量，不应该继续人为增加寄存器。**
